# Отчёт по аудиту rootlost.ru: что исправлено

Дата работы: 22 сентября 2026 года. Проект: `portfolio-site` (портфолио Александры Мельниковой).
Основание: внешний аудит от 21 сентября 2026 года (файл `Rootlost_audit_DSH_2026-09-21.md`).

Коротко: путь обращения переделан на честный (копирование ≠ отправка), каждый кейс стал
отдельной индексируемой страницей со своим адресом и метаданными, текст виден в исходном HTML
без JavaScript, карта сайта собирается из того же списка страниц, страница ошибки стала
компактной, а футеры кейсов больше не ведут в никуда.

**Портфолио выложено на хостинг 22.09.2026** (`/www/rootlost.ru`), коды ответов и метаданные
проверены на живом сайте — таблица в разделе 4. Демо-сайты правятся локально и пока **не
выложены**: их правка ждёт вашего решения (раздел 7).

### Портфолио на живом сайте после выкладки 22.09.2026

Перед выгрузкой снята копия прежней версии (223 файла, `/.backup/deploy-2026-09-22/`) — это
точка отката. Затем выгружены 62 файла сборки и проверены ответы:

| Адрес | Ответ | Что проверялось |
| --- | --- | --- |
| `/` | 200 | заголовок и canonical свои, og:image на месте |
| `/case.html?work=kitstroy` | 301 → `/cases/kitstroy/` | постоянный переход со старого адреса |
| `/cases/` | 200 | каталог кейсов, свой canonical |
| `/cases/kitstroy/`, `/cases/sextant/` | 200 | уникальные title, canonical, og:image (`/og/<slug>.jpg`) |
| `/cases/unknown-case/` | 404 | своя страница ошибки, 17,8 КБ вместо 769 КБ |

| `/index.html` | 301 → `/` | дубль главной закрыт |

Разбор восьми живых адресов (главная, каталог и шесть кейсов) на ширине 1440:
непоявившихся блоков 0, переполнения нет, дефектов нет.

Отдельно проверено, что `/render.html` отдаёт 404: служебный файл сборки в выгрузку не попал.

`/wp-login.php` отвечает 200, но это не наш файл и не наш ответ: так хостинг REG.RU встречает
запросы к этому адресу (ставит cookie `RCPC` и перенаправляет страницу сама на себя).
До Apache запрос не доходит, поэтому правило 410 к нему не применяется. Это защита хостинга,
а не работающая установка WordPress: `/wp-admin/` и `/wp-json/` отдают 404, `/xmlrpc.php`
обрывает соединение.

## 5. Серверная часть: что подготовлено и что осталось

Файл `public/.htaccess` попадает в сборку и выгружается вместе с сайтом. В нём:

1. **Старые адреса кейсов** — точная карта: `/case.html?work=sextant` → `/cases/sextant/` (301),
   и так для всех шести. Правило срабатывает только при известном `work`, поэтому неизвестный
   параметр не перенаправляется «куда-нибудь», а попадает на 404. `/case.html` без параметра
   ведёт в каталог `/cases/`.
2. **`index.html` → `/`** — только на верхнем уровне: правила без ведущего слэша не заходят в
   `/sextant/` и `/remont/`, поэтому эти сайты не затрагиваются.
3. **Путь без завершающего слэша** — `/cases/sextant` → `/cases/sextant/`.
4. **`ErrorDocument 404 /404.html`** — своя компактная страница ошибки с кодом 404.
5. **Кеширование** — HTML не кешируется надолго (иначе после выкладки браузер держал бы ссылки
   на удалённые файлы сборки), файлы с хешем в имени кешируются на 45 дней.

Правила HTTPS и www **включены 23.09.2026** первым пунктом в блоке `mod_rewrite`. Схему
запроса сообщает nginx заголовком `X-Forwarded-Proto`; перед включением это проверено пробой
(раздел 9). Условие сравнивается строго с `http`, поэтому на защищённом соединении оно не
срабатывает и цикл невозможен. Если бы хостинг перестал отдавать заголовок, правило просто
не сработало бы — сайт продолжил бы отвечать, а не зациклился.

`Options -Indexes` в начале файла закрывает листинг каталогов.

## 8. Как это устроено после правок

**Один список адресов.** `src/data/manifest.ts` описывает страницы: адрес, файл, заголовок,
описание, дату обновления, признак индексации. Из него собираются статические страницы, карта
сайта, `robots.txt` и проверки. Добавить кейс — значит добавить запись в данные сайта и строку в
манифест; всё остальное соберётся само.

**Сборка страниц.** `npm run build` собирает проект, затем открывает свои же страницы в
headless-браузере и снимает готовую разметку в файлы `dist`. Поэтому:
- текст, H1 и ссылки есть в исходном HTML — их видят и роботы, и посетители без JavaScript;
- React после загрузки подхватывает готовую разметку и оживляет интерактив;
- если страница отрисовалась не полностью, сборка падает (`assertContent` в `prerender.mjs`),
  а не выкладывает пустую оболочку.

**Один вход для всех страниц.** `src/entries/render.tsx` определяет страницу по адресу. Раньше у
каждой страницы был свой скрипт, и страница кейса могла загрузить точку входа главной и
подменить разметку — от этой ошибки теперь есть проверка и в коде, и в тестах.

**Путь обращения.** `MessageBuilder` — один компонент для квиза и страниц кейсов. Копирование,
открытие Telegram и письмо — три разных действия; успех сообщается только после успешного
копирования; при отказе текст выделяется и остаётся на странице.

### 9.3. Проба `X-Forwarded-Proto` и включение зеркал

Схему запроса Apache на этом хостинге не видит: перед ним стоит nginx. Чтобы не гадать, на
сайт на несколько минут был положен `.htaccess` с одной пробой — он ничего не перенаправлял,
а только показывал значение заголовка в ответе:

```apache
SetEnvIf X-Forwarded-Proto "^https$" PROBE_XFP_HTTPS=1
SetEnvIf X-Forwarded-Proto "^http$"  PROBE_XFP_HTTP=1
Header always set X-Probe-Xfp-Https "%{PROBE_XFP_HTTPS}e"
Header always set X-Probe-Xfp-Http  "%{PROBE_XFP_HTTP}e"
```

Ответ сервера: по `https://rootlost.ru/` — `X-Probe-Xfp-Https: 1`, по `http://rootlost.ru/` —
`X-Probe-Xfp-Http: 1`. Значит заголовок приходит и различает схему; пробу сняли, в репозитории
её нет. После этого в `public/.htaccess` включены переходы:

```apache
RewriteCond %{HTTP:X-Forwarded-Proto} =http [NC]
RewriteRule ^(.*)$ https://rootlost.ru/$1 [R=301,L]

RewriteCond %{HTTP_HOST} ^www\.rootlost\.ru$ [NC]
RewriteRule ^(.*)$ https://rootlost.ru/$1 [R=301,L]
```

| `https://www.rootlost.ru/` | 301 → `https://rootlost.ru/` |

### 9.5. Файлы подтверждения прав в поисковых кабинетах

Владелец заводит сайт в Яндекс.Вебмастере и Google Search Console: оба сервиса проверяют права
по файлу в корне. Файлы лежат в `public/` и попадают в каждую сборку:

| Файл | Содержимое | Состояние |
| --- | --- | --- |
| `yandex_cae8d1b04de0f494.html` (161 Б) | `Verification: cae8d1b04de0f494` | права подтверждены 23.09.2026 |
| `googlea24d5f83953f726c.html` (53 Б) | `google-site-verification: googlea24d5f83953f726c.html` | выложен 23.09.2026 |

Ловушка, ради которой это описано: сервис скачивает файл **по тому адресу, который добавляют
в кабинет**. После включения зеркал (9.3) любой адрес кроме `https://rootlost.ru/` отвечает
переходом 301, а часть проверок переход не проходит — файл «не найден». Поэтому правило отдачи
файлов стоит **выше** правил зеркал:

```apache
RewriteCond %{REQUEST_URI} ^/(yandex|google)[A-Za-z0-9_]+\.html$ [NC]
RewriteRule ^ - [L]
```

Живая проверка 23.09.2026: файл Google отдаётся **200 по всем четырём адресам**
(`https://rootlost.ru/…`, `https://www.rootlost.ru/…`, `http://rootlost.ru/…`,
`http://www.rootlost.ru/…`), скачанное содержимое совпадает с исходником побайтово
(sha256 `9f54d352…`), файл Яндекса — 200. Переходы зеркал при этом целы: `http://rootlost.ru/`
и `https://www.rootlost.ru/` → 301, `https://rootlost.ru/` → 200 без переходов, `/cases/` → 200,
неизвестный адрес → 404. Выложено 64 файла в `/www/rootlost.ru`, проверка сборки:
`check-seo.mjs dist` — 13 страниц, замечаний нет.

В `robots.txt` файлы подтверждения **не** закрыты: закрытый файл сервис прочитать не сможет и
права не подтвердит. Закрывать их от индексации имеет смысл только после подтверждения и не
через `robots.txt`.
